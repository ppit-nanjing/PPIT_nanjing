## What's built and working

**Full application, every module from the original IA — every page is real, no mockups.** Public flows (Events, Jobs, Career, Join Us, Sensus, Inventory borrowing) all write to Neon via server actions. Admin console (`/console`, not `/admin` — deliberately less guessable) has working CRUD for every module: Users, Organization, Events, Inventory, Reports, Documentation, and Feedback.

- Next.js 16 (App Router, Turbopack) + TypeScript + Tailwind v4, design tokens from [Design System Overview.md](./Design%20System%20Overview.md).
- **Neon Postgres** (`ap-southeast-1`) via Drizzle ORM — schema matches [Entity Relationship Diagram.md](./Entity%20Relationship%20Diagram.md). Real org structure seeded from the recruitment guidebook (3 Departemen, 9 Divisi, BPH), plus the 9 known PPI Tiongkok regional branches and the actual 2026/2027 recruitment period dates.
- **Auth.js** (Google + Credentials/email-password providers, **JWT sessions**) — session carries `adminScope` (`"full" | string[] | null`, computed from `accessTier` + department `adminModuleScope`/`grantsFullAdminAccess`) and `emailSubscribed`. `isAdmin` is now a derived convenience boolean (any non-empty scope), not the source of truth. Session strategy is `jwt` (not `database`): `@auth/core`'s Credentials branch only persists JWT sessions, so credentials logins can't use the `sessions` table — that table is now unused but left in schema for stability. The `jwt` callback bakes `user.id` in at sign-in and the `session` callback re-derives `adminScope`/`isAdmin`/`emailSubscribed` from the DB on every request, so admin scope stays live.
- **Public pages**: Home, About, Organization Structure, Regional Branches, AD/ART, Terms, Privacy, News (list+detail), Gallery (list+album), Events (list+detail+register+QR ticket), Jobs (list+detail+apply), Career Center + Guide + Mentorship, Join Us (open/closed states), Sensus (3-step wizard, upsert), Inventory catalog + borrow request, Login, Profile (subscription toggle), 404, Maintenance.
- **Admin console** (`/console/*`) — layout gates on "any admin access at all"; each module page + its server actions additionally call `requireModuleAccess`/`hasModuleAccess` (`src/lib/admin-scope.ts`) so a 'scoped' user (e.g. Divisi Logistik) only sees and can write to the modules their department is actually scoped to, not every module a 'full'-tier BPH member sees. Sidebar nav filters itself the same way.
  - `/console` — dashboard (real feedback counts), visible to anyone with any admin access
  - `/console/users`, `/console/organization`, `/console/feedback` — full tier only (not delegable, no seed row scopes them)
  - `/console/events` — create/edit, registration roster, check-in
  - `/console/inventory` — add items, approve/reject/return borrow requests (atomically adjusts `availableQuantity`)
  - `/console/content` — news articles (draft/publish) + gallery albums/photos — was a real gap (no way to publish anything) until this batch
  - `/console/reports` — real sensus aggregate tallies + CSV student export (also reachable via the `sensus` scope key, see `admin-scope.ts` comment)
  - `/console/notifications` — **new 2026-08-17**, full-tier only: edit the wording of the 7 automatic notifications the app sends. Defaults live in code (`src/lib/notification-templates.ts`); a `notification_templates` row is an *override*, and "Kembalikan ke bawaan" deletes the row rather than writing a second copy of the default. `notification_templates` is no longer an unused table. In-app channel only — no email/push provider exists, and the page says so instead of offering a dead channel picker.
  - `/console/docs` — help articles by section (5 seeded from what's actually built) + editable in-app, `/console/docs/changelog` for release notes — visible to anyone with any admin access, same as Dashboard

## Decisions worth knowing about (so they don't get re-litigated)

- **Neon over Supabase** — the user provided a live Neon connection string mid-project. Auth (Auth.js) and Storage (Vercel Blob, not yet wired) were assembled separately since Neon doesn't bundle them.
- **`/console` not `/admin`** — deliberately less guessable path; the real access boundary is the session check on the layout, not the name.
- **Motion, not GSAP/Aceternity/a full UI kit** — matches the "no heavy libraries" constraint in the original animation PRD.
- **`proxy.ts` not `middleware.ts`** — Next.js 16 renamed the convention.
- **Self-service sign-up added (reverses the earlier "OAuth-only" decision)** — accounts can now be created two ways: Google OAuth (unchanged) and a new email/password path at `/signup` (Credentials provider, bcrypt-hashed `passwordHash` in `users`). There is still **no admin "create user" provisioning flow** — that remains a deliberate omission; new accounts self-register, then an admin assigns role/department after first sign-in. Account-collision rule: signing up with an email that already has a Google-only account is rejected with "use Google instead" (we don't silently link by email, since there's no email verification to make that safe); the `users.email` unique constraint is respected, never worked around.
- **Borrow requests decrement stock on admin approval, not on submission** — a pending request doesn't reserve inventory.
- **Tidak ada kolom `account_type`/"tipe akun" — status keanggotaan DITURUNKAN** (2026-08-21, `src/lib/membership-status.ts`). Tiga status: **Anggota** (sensus lengkap + `branch = "Nanjing"`), **Cabang lain** (sensus lengkap + cabang ≠ Nanjing), **Tamu** (belum/tidak lengkap mengisi sensus). Alasan menolak kolom tipe: ia akan langsung berselisih dengan sensus — orang mengisi sensus belakangan atau pindah cabang, lalu yang benar yang mana, kolomnya atau `branch`-nya? Yang berubah bukan orangnya, tapi seberapa banyak yang kita tahu tentang dia; itu keadaan data, bukan tipe akun. Label "non-Nanjinger" juga sengaja tidak dipakai: kalau `branch = "Shanghai"`, menulis "non-Nanjinger" justru membuang informasi yang sudah dipunya. **Batasnya:** "Tamu" adalah satu ember campur — dari sensus saja, "warga Nanjing yang belum sempat isi" dan "tamu dari luar" tidak bisa dibedakan. Itu sebabnya `event_registrations.branch` ada (di bawah).
- **Pendaftaran acara menanyakan asal cabang, tapi hanya ke yang sensusnya belum lengkap** (2026-08-21). Satu dropdown di form pendaftaran, disimpan di `event_registrations.branch` + opsi "Bukan mahasiswa Indonesia di Tiongkok". **Jawaban sekali-pakai untuk acara itu saja** — tidak disalin ke profil user dan tidak pernah dipakai untuk rekap ke pusat (sensus yang berwenang, lihat `effectiveBranch()`); menyalinnya akan membuat dua nilai yang bisa berselisih. Yang sensusnya sudah lengkap tetap satu klik seperti sebelumnya — cabangnya sudah diketahui, menanyakan ulang cuma menambah gesekan. Roster di `/console/events/[id]` sekarang punya kolom "Asal" (cabang + status keanggotaan). Alternatif yang ditolak: mewajibkan sensus untuk semua acara — itu akan memblokir tamu luar, padahal `events.requiresSensus` defaultnya `false`, artinya organisasi memang sengaja mengizinkan mereka.
- **Identitas: Gmail adalah kunci akun di portal, nomor paspor adalah kunci orang di rekap pusat** (2026-08-21). `users.email` sudah `UNIQUE`, jadi dua akun dengan Gmail sama tidak mungkin. Tapi satu orang bisa punya DUA Gmail (pribadi + kampus) dan sebelumnya bisa mengisi sensus dua kali — terhitung dua anggota di sini dan terkirim dobel ke pusat, karena `sensus_profiles.user_id` yang unik tidak menghalangi itu. Sekarang `sensus_profiles.passport_number` `UNIQUE` (NULL boleh berulang: profil yang belum diisi memang belum punya nomor). Email bukan kuncinya karena **form pusat tidak punya field email sama sekali** — nomor paspor satu-satunya identitas yang benar-benar unik per orang di sana. **Kembar ditolak, tidak dipindahkan otomatis:** nomor paspor di form ini adalah klaim identitas yang belum diverifikasi siapa pun, jadi memindahkan profil lama ke akun baru secara otomatis berarti siapa saja yang tahu nomor paspor orang lain bisa mengambil alih baris sensusnya. Penyelesaiannya lewat pengurus: hapus akun yang tidak dipakai di `/console/users` (sensus ikut terhapus lewat cascade). Ditolak sejak langkah Biodata (`saveSensusStep`), bukan menunggu submit akhir.
- **Form Sensus disamakan field-per-field dengan form PPI Tiongkok pusat** (2026-08-21) — alasannya: data yang dikumpulkan di sini akan dimasukkan ulang ke sistem pusat, jadi apa pun yang kita kumpulkan di luar field mereka tidak punya tempat, dan apa pun yang kurang harus dikejar satu-satu ke tiap anggota. Konsekuensi yang sengaja diambil: (1) Asal Provinsi jadi dropdown 38 provinsi (`src/lib/indonesia-provinces.ts`), bukan teks bebas, supaya ejaannya seragam saat direkap; (2) Nama Universitas jadi dropdown bertingkat yang terkunci sampai Asal Cabang dipilih, sumbernya `branch_universities`; (3) Nomor Telepon Aktif dikunci +86 (WhatsApp tetap +62/+86); (4) WeChat ID divalidasi 6-20 karakter `[A-Za-z0-9_-]` persis seperti aturan yang tertulis di form pusat; (5) kelengkapan semua field wajib ditegakkan di server (`validateSensus` di `src/lib/sensus-form.ts`, dipakai bersama oleh wizard dan server action) — sebelumnya `completionStatus: "complete"` bisa tersimpan dengan field kosong. Ekspor `sensus_summary` di `/console/reports` ikut diperluas dari 5 kolom jadi seluruh field pusat, urut sama seperti form mereka — itulah berkas yang dipakai pengurus untuk memindahkan data. **Yang sengaja TIDAK ditiru:** batas unggah 205 KB + perkecil-otomatis milik form pusat — penyimpanan kita tidak punya batas itu dan `ImageUploadCropper` belum bisa mengecilkan gambar; kalau berkas kartu mahasiswa nanti harus diunggah ulang ke form pusat, ukurannya perlu dicek manual dulu.
- **Git commits are one-file-per-commit** by explicit user preference — keep doing this for future changes. (Slipped twice so far and bundled a few files together when moving fast through a big batch — not rewriting the already-pushed history for those, but the discipline should hold going forward.)
- **`npm run build` passing does NOT mean the live Neon schema is in sync**, and doesn't mean auth actually works. Next.js's build only statically analyzes routes — it never actually executes a query or runs a real sign-in — so two real bugs stayed invisible through many green builds and only surfaced as a live 500 the first time someone completed Google sign-in in production:
  1. Schema drift: `drizzle-kit push` had only been run once at project start; every schema.ts change since (accounts/sessions tables, feedback, notifications, reports...) never reached Neon. Fixed 2026-08-15 by re-running `drizzle-kit push --force`.
  2. **The real culprit**: `DrizzleAdapter(db)` in `src/auth.ts` was called without its required second argument (the table mapping). Without it, `@auth/drizzle-adapter` silently falls back to its own built-in table definitions - literally named `user`/`account`/`session`/`verificationToken` (singular, inconsistent casing) - which don't exist in this schema (`users`/`accounts`/`sessions`/`verification_tokens` do). Every sign-in attempt threw `NeonDbError 42P01: undefined_table` querying a table name that was never actually created. Fixed by passing `{ usersTable, accountsTable, sessionsTable, verificationTokensTable }` explicitly. This also required renaming `accounts`' token columns (`refreshToken` → `refresh_token`, etc.) to match the adapter's expected property *names* exactly, not just matching via the DB column-name string - the adapter accesses these as plain JS properties.
  - **Lesson: a passing build is not a signal that auth actually works.** After any change touching `src/auth.ts` or the adapter-facing tables, the only real test is an actual sign-in attempt (locally with `.env` configured, or in production) — TypeScript and the build step can't catch either of these two bug classes.
